# Service 代码评审

默认只读，不修改代码。优先报告会导致数据泄露、越权、错误提交、启动失败、契约破坏或发布阻塞的问题，再报告测试缺口和次要维护问题。

## 工作流程

1. 确认评审范围和比较基线。若用户未指定分支、提交或 diff，读取当前状态并明确使用的范围；不要擅自扩大到整个仓库历史。
2. 读取根目录 `AGENTS.md`、`service/AGENTS.md`、相关 `.codex/` 规则，以及改动涉及的 Controller、Service、DAO、DTO/DO、配置、迁移、seed 和测试。
3. 沿真实调用链检查：路由 → 依赖/认证 → Service 业务规则 → DAO/事务 → 外部副作用 → 响应/日志。不要只根据文件名或注释推断行为。
4. 按优先级检查：
   - 认证、RBAC、管理员保护、租户和数据范围绕过。
   - 跨请求 `AsyncSession`、提交/回滚、审计事务、并发、幂等和重复副作用。
   - DTO/路由/响应包装/分页/文件流契约不一致。
   - 动态路由遮蔽静态路由、环境变量导入、Redis/MySQL 启动依赖和生命周期泄漏。
   - Alembic 顺序、外键索引、初始化 SQL 幂等、权限 seed 缺失。
   - Token、密码、验证码、密钥、完整敏感 payload 和真实数据泄露。
5. 每个发现都给出文件和行号、严重级别、可复现路径、实际影响、根因和最小修复方向。区分确定缺陷、能力缺失和未验证风险。
6. 从头重新检查一次已修复的结论，不因为旧评审记录或提交信息而默认问题已消失。
7. 评审结束只运行不改变状态的验证，例如目标测试、静态搜索、离线迁移 SQL 和 `git diff --check`；报告 Docker、真实数据库、Redis、第三方和生产验证是否未执行。

## 输出顺序

1. Findings：按严重性从高到低，带文件/行号和证据。
2. Open questions / assumptions：只列会影响结论的事项。
3. Change summary：简短说明已覆盖范围。
4. Test gaps / residual risk：说明未执行的外部和并发验证。

不要把代码风格偏好写成缺陷，不要在没有利用路径或行为证据时泛化为安全问题。详细检查项见 [review-checklist.md](references/review-checklist.md)。
